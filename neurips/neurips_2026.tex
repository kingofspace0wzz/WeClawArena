\begin{abstract}
Human-centered agentic social networks, in which each user is served by a persistent personal AI assistant and assistants routinely speak with one another on their principals' behalf, are becoming a reality; open-sourced personal-assistant frameworks such as OpenClaw \citep{openclaw2025} supply the per-user building block. Deploying such networks exposes three questions that isolated-agent environment does not see: \emph{multi-party collaboration}, whether personal agents from multiple users can effectively collaborate on shared tasks under different social contexts; \emph{security}, whether the network can contain attacks that spread through peer messages; and \emph{privacy}, whether user privacy holds as information flows across the network. An \emph{auditable} runtime system is needed to answer these questions, so that an operator can reconstruct what each assistant did, decide whether declared rules were obeyed, and trace responsibility when a failure spreads across the graph. To this end, we introduce \emph{ClawSocialArena}, the first auditable runtime system built for human-centered agentic social network, with a benchmark covering multi-party collaboration, security, and privacy side by side. Our three contributions are (i) an audit-first runtime of persistent personal-AI-assistant agents for human-centered agentic social network; (ii) the \emph{Social Auditability Framework} (SAF) with \emph{Multi-Party Social World Modeling} (MPSWM), an online per-pair record of what each agent has told and learned from every peer, on which checking declared rules and tracing who caused a violation through the chain become possible; and (iii) a benchmark of $150$ scenarios with four verifiable task families and a three-axis attacker taxonomy. 
\end{abstract}

\section{Introduction}
\label{sec:intro}

Human-centered agentic social networks, in which each user is served by a persistent personal AI assistant and assistants routinely speak with one another on their principals' behalf, are becoming a reality. Open-sourced personal-assistant frameworks such as OpenClaw \citep{openclaw2025} supply the per-user building block: each user's assistant runs as a persistent process that manages private memory, connects to external channels, and proactively initiates actions on the user's behalf. Once such assistants are deployed across users who already interact with one another, their cross-user traffic traces out a social graph, on which the assistants coordinate scheduling across households, aggregate a team's availability for a manager, negotiate on behalf of their principals in group chats, and escalate, delegate, and summarize without explicit human prompting. Generative-agent studies \mbox{\citep{park2023generative}}, large-scale social simulations \mbox{\citep{oasis2024,piao2025agentsociety}}, early observational studies of agent-native platforms \mbox{\citep{jiang2026moltbook,moltbook2026socialization,moltnet2026,collective2026moltbook}}, and interoperability protocols such as Agent-to-Agent \mbox{\citep{googlea2a2025}} all indicate that running this regime with real persistent assistants is a near-term reality rather than a research hypothetical.

Deploying such networks forces three new questions on the operator, none of which map cleanly onto existing benchmarks. First, a \emph{multi-party collaboration} question: when four assistants must find a meeting slot that respects four principals' constraints, or when a hub aggregates private inputs from spokes into a single decision, can the network actually complete the task, and do legitimate participants reach the target state when a peer actively tries to block them? Second, a \emph{security} question: when one assistant's inbound channel is compromised by a prompt injection, or when a delegation chain is abused, or when shared memory is poisoned, how far does the attack propagate through the graph and which downstream principals are harmed? Third, a \emph{privacy} question: when a disclosure made in one thread propagates through summaries, retrievals, and peer-to-peer messages, when is a joint inference across what three assistants now know a violation of a cross-user boundary that no single message breached? Answering any of these three questions after the fact requires the deployed system to be \emph{auditable}: the operator must be able to reconstruct what each assistant did (including the memory writes, compressions, and retrievals that a tool-call-centric audit would miss), to decide each declared policy from the recorded state, and, when a failure propagates, to attribute responsibility along the inference chain that produced it.

\textbf{Two partial views of the problem.} Two literatures address parts of this picture, and neither addresses it for deployed multi-party settings. \emph{Social-agent benchmarks} evaluate collections of LLM agents in scripted scenarios: SOTOPIA \citep{zhou2024sotopia} for social intelligence, ConfAIde \citep{mireshghallah2024confaide} and PrivacyLens \citep{shao2024privacylens} for contextual-integrity awareness, MAGPIE \citep{juneja2025magpie} for multi-agent contextual privacy, AgentLeak \citep{elyagoubi2026agentleak} for end-to-end leakage, CIMemories \citep{cimemories2025} for persistent memory, and AgentSocialBench \citep{wang2026agentsocialbench} for a broad multi-category scenario set. These frameworks score \emph{outcomes} from static scenario specifications, episode by episode, typically with LLM-as-judge pipelines \citep{zheng2023judging}, and without exposing a runtime around the agents, let alone an audit substrate. They also concentrate on privacy and largely omit multi-party task collaboration and targeted security attacks. \emph{Auditability frameworks} make post-deployment audit questions first-class: Auditable Agents \citep{nian2026auditable} defines the necessary conditions for a defensible verdict, and systems such as Agent Audit \citep{zhang2026agentaudit} supply static-analysis pipelines for single-agent tool-use code. This work targets the single-agent setting; its action model centers on tool invocations, its policy checks run per-record, and its integrity guarantees are append-only within one process. In a social network, leakage and harm flow through peer messages, retrieval side channels, memory compression, and joint inference over partial observations, none of which is addressed by a per-agent tool-call log. Cooperative multi-agent frameworks \citep{hong2024metagpt,wu2023autogen,chen2024agentverse,li2023camel,qian2025scaling} assume shared rewards and bypass the multi-principal problem entirely. In parallel, the move from one-shot to \emph{continuous} evaluation has already exposed large gaps between instantaneous capability and long-horizon performance in the software-agent domain \citep{deng2026evoclaw}; an analogous move for social agents, made under the constraint that auditability itself is a measurable property of the deployed system, has not been made.

\textbf{Contributions.} ClawSocialArena closes this gap by delivering, jointly, a runtime around real personal-AI-assistant agents and a benchmark that exercises multi-party collaboration, security, and privacy under that runtime. Auditability is \emph{measurable} through a five-dimension scoring framework and \emph{interventional} through a single three-way switch at the central audit gateway.
\begin{itemize}
    \item \textbf{C1 --- an audit-first runtime for multi-party agentic social networks.} Every scenario runs as a live deployment of persistent personal-AI-assistant agents with a central audit gateway as the sole cross-agent hop. A three-way switch (\textsc{baseline}, \textsc{passive}, \textsc{enforce}) selects passthrough, record-only, or block-and-rewrite enforcement, so that every measurement can be compared against a no-audit baseline and auditability becomes an experimental intervention rather than a descriptive property.
    \item \textbf{C2 --- the Social Auditability Framework (SAF) with Multi-Party Social World Modeling (MPSWM).} MPSWM is an online, per-pair record of what each agent has told and learned from every peer, maintained by the gateway and updated before any policy hook fires. On top of it, SAF defines five dimensions (action recoverability, epistemics-aware policy checkability, inference-chain attribution, asymmetric evidence integrity, phase-scoped policy auditability), each with a mechanically emitted ground-truth artifact and a declared pass threshold, combined as a weighted geometric mean that prevents a system from compensating for failure on one dimension with excellence on another. Three named \emph{motivating examples} (Figure~\ref{fig:vignettes}) show cases where a single-agent auditor returns a compliance verdict that SAF correctly overturns.
    \item \textbf{C3 --- a benchmark of $150$ scenarios covering multi-party collaboration, security, and privacy.} We lift AgentSocialBench's \citep{wang2026agentsocialbench} seven social categories from static specifications into runnable multi-party scenarios with four verifiable task families scored by deterministic terminal predicates (no LLM-as-judge in the headline), and a three-axis attacker taxonomy covering multi-party collaboration, security, and privacy. Ground-truth artifacts are emitted mechanically by a four-layer generator, and a $40$-scenario annotator sample reports inter-annotator agreement as a floor on generator quality.
\end{itemize}

\section{Human-Centered Agentic Social Network}
\label{sec:problem}

This section formalizes the deployment setting. To fix intuitions, consider three users (Alice, Bob, and Charlie), each served by their own persistent personal-AI-assistant. In a scheduling conversation with her own assistant, Alice mentions that she has recently returned from an overseas trip; the assistant writes a structured note to long-term memory. A day later, Bob's assistant talks with Alice's assistant about travel preferences on one thread, and with Charlie's assistant on another. A week after that, Charlie's assistant researches an unrelated question on his behalf and, as part of routine context management, retrieves a compressed summary that silently includes Alice's earlier disclosure. Whether a privacy commitment has been violated in this chain depends on three questions: \emph{what each assistant actually did} (including the memory write, the compression, and the retrieval, not only overt messages); \emph{what each downstream assistant could be expected to know} at the point it acted; and \emph{how those actions combine} into a responsibility chain. An audit that ignores any of the three cannot deliver a defensible verdict. The remainder of this section gives the setting and the action model formal footing; the framework that uses them follows in \S\ref{sec:saf}.

\textbf{Setting.} Let $\mathcal{N}$ be a finite set of persistent personal-AI-assistant agents, each $i\in\mathcal{N}$ serving exactly one principal. We call this the \emph{personal-agent setting}, and it excludes market-of-agents and multi-agent-team-per-user configurations (\S\ref{sec:discussion}). Over a scenario of $T$ turns, agent $i$ emits a sequence of \emph{actions} $a_i^{(1)},\dots,a_i^{(T)}$. An action is any observable unit of agent behavior whose audit-relevance has been declared in advance; it is the atomic unit the log will record and the framework will reason about.

\textbf{Actions as the unit of audit.} Actions fall into three analytic classes. \emph{First-class} actions are agent-initiated and visible across the graph: LLM invocations, tool calls, outbound messages to peer agents, writes to long-term memory, and the spawning of delegated subagents. \emph{Control-plane} actions are the policy verdicts that the gateway produces when an audit hook fires. \emph{Side-channel} actions capture the information flows that a tool-call-centric log typically elides: the return of a tool observation into an agent's working context, a retrieval from an external store, the compression of a long context window into a shorter summary, and the periodic writing of that summary to long-term memory. In the running example, Alice's memory note is a first-class action, but the compression performed inside Charlie's agent and the retrieval that injected its output into Charlie's context are both side channels, and the violation could not have been detected without either of them. Promoting side channels to first-class status in the audit log is the single most important modeling commitment of our framework, because it is what permits leaks flowing through retrieval and summarization to be attributed at all.

\section{The Social Auditability Framework}
\label{sec:saf}

Given the action log of \S\ref{sec:problem}, the audit problem is to produce, for each declared policy, a comply-violate-unknown verdict together with an attribution subgraph over the agents whose actions constitute the responsibility chain. The Social Auditability Framework (SAF) delivers such verdicts mechanically. At its core is \emph{Multi-Party Social World Modeling} (MPSWM), an online, per-pair epistemic state that tracks what each agent has been told, has learned, and has committed to; on top of MPSWM the framework defines five continuous scoring dimensions whose ground-truth artifacts are emitted mechanically by the scenario generator. The rest of this section defines MPSWM, illustrates the framework with three motivating examples, presents the five dimensions, and describes the three mechanism classes that realize them across the run lifecycle.

\subsection{Multi-Party Social World Modeling}
\label{sec:saf:mpswm}

Many multi-party privacy and commitment obligations depend on \emph{what each party currently knows}, not only on what has been said to it. The reply ``I cannot confirm whether Alice traveled recently'' is a violation if the listener has already been told so by someone else, and a routine refusal otherwise. For each ordered pair of agents $(i,j)$ we maintain a \emph{Multi-Party Social World Model} state $\mathrm{MPSWM}_{ij}$ with six components: the set of items that $i$ has disclosed to $j$, each tagged with the action that produced it; the symmetric set of items $i$ has learned from $j$; commitments $i$ has made to $j$, each tagged with the social phase in which the commitment was made; a joint-decidability function that maps each item to \textsf{decidable}, \textsf{undecidable}, or \textsf{violated} given the combined MPSWM state of all peers at the relevant turn; the phase of last interaction; and a $[0,1]$ trust estimate reserved for affinity-modulated scenarios. MPSWM is a deterministic function of the action log: outbound messages, memory writes, and tool observations extend $\mathrm{MPSWM}_{ij}$ through a structured disclosure field carried in their payload; abstraction-upgrade and revocation actions retract from it. The gateway updates MPSWM online, immediately after each action is appended to the log and \emph{before} policy hooks run, so that hooks see the freshest epistemic state. We call a policy $\pi$ \emph{jointly decidable} at turn $t$ if every variable it quantifies over resolves under the MPSWM states of the agents it mentions at that turn; otherwise $\pi$ is \emph{undecidable}, not unknown but unanswerable from the available record. Joint decidability is strictly stronger than per-record decidability: Alice's utterance to Bob can be per-record compliant (``I mentioned a trip'') while the combined state of $\mathrm{MPSWM}_{\mathrm{Alice},\mathrm{Bob}}$ and $\mathrm{MPSWM}_{\mathrm{Charlie},\mathrm{Bob}}$ makes Alice's trip identifiable with Charlie's recent absence. That distinction is what separates inferential leakage (\S\ref{sec:saf:vignettes}) from a trivially compliant baseline. MPSWM is not bolted onto SAF: it is the runtime state that makes SAF's policy-checkability and attribution dimensions decidable at all, and a scoring pipeline that lacks MPSWM can produce recoverability, integrity, and approximations to phase-scoped checks but cannot produce the other two.

Given the action log $\mathcal{L}=\bigcup_i\{a_i^{(t)}\}$, the MPSWM state trajectory, and a declared policy set $\Pi=\{\pi_1,\dots,\pi_m\}$, the audit verdict for each $\pi\in\Pi$ is $V(\pi)\in\{\textsf{comply},\textsf{violate},\bot\}$ together with an attribution subgraph over $\mathcal{N}$. Four properties make the verdict \emph{defensible}: \emph{recoverability} ($\mathcal{L}$ records the actions on which $V$ depends), \emph{decidability} (each $\pi$ is jointly decidable from $(\mathcal{L},\mathrm{MPSWM})$), \emph{attribution} (when $V=\textsf{violate}$, the subgraph correctly identifies the responsibility chain), and \emph{integrity} (every record used to derive $V$ meets its class-specific integrity requirement). When attribution is required, the framework labels each node on the chain with one of five roles. \textbf{L0} (root) is the action that first introduced the disclosed content into the social graph. \textbf{L1} (inference-enabled) is a downstream step that was possible only because of a prior L0 or L1 action further upstream. \textbf{LX} (cascaded) is a propagation through a third agent that neither originated nor necessarily intended the leak. \textbf{LR} (repaired) is a later action by the source that retracts, abstracts, or revokes the disclosure. \textbf{LF} (forgotten) is a disclosure whose evidence decayed from downstream contexts without active repair. In the running example, Alice's original note is L0, Bob's aggregated summary is L1, Charlie's retrieval is LX, and, had Alice later issued an abstraction upgrade, that would be LR on the same chain. SAF operationalizes the four defensibility properties, adds a fifth (phase-scoped auditability) for policies tied to specific phases of interaction, and makes the L0--LF labels mechanical rather than hand-assigned.

\subsection{Motivating examples}
\label{sec:saf:vignettes}

Figure~\ref{fig:vignettes} presents three scenarios that ship as named, load-bearing benchmark items inside the $150$. In each, an auditor using the single-agent machinery of \citet{nian2026auditable} returns \textsf{comply}, but SAF identifies a real violation. The examples are not hand-picked adversarial cases; they are the simplest witnesses of three distinct structural limitations, and each runs as an actual multi-party deployment with real personal-AI-assistant agents.

\textbf{Inferential leakage (joint decidability).} Agents $A$, $B$, $C$ interact in a group channel. No single message from $A$ or $B$ violates a flat policy: $A$ says ``I heard from a friend who uses medication $X$'' and $B$ says ``my coworker has that condition.'' Flat policy checks evaluate each record independently and pass. SAF computes \emph{joint} decidability: when both disclosures reach $C$, $\mathrm{MPSWM}_{A,C}$ and $\mathrm{MPSWM}_{B,C}$ jointly make $A$'s friend identifiable as $B$'s coworker, violating a declared cross-user boundary on co-identification.

\textbf{Cross-delegation attribution.} Agent $C$ executes a harmful action directed at user $D$, following a summary written earlier by $B$, which was in turn derived from a disclosure made by $A$. A vanilla responsibility chain stops at $C$, the immediate executor. SAF's inference-chain attribution traces L0 responsibility back to $A$ by following the summary-write edge to $B$ and the tool-observation edge from $B$'s summary into $C$'s working context.

\textbf{Partial-log recovery.} Agent $A$'s log segment is corrupted mid-run (simulated by the gateway dropping records emitted by $A$ after a chosen turn index). A vanilla recoverability check fails outright and the audit cannot proceed. SAF instead reconstructs $A$'s actions from peers' logs via the cross-agent references carried in each inbound message, producing a usable attribution graph whose nodes carry confidence weights reflecting the indirect evidence.

\end{table}

\textbf{Recoverability ($s$).} Ground truth is a shadow log double-written by the gateway alongside the primary hash-chained log; the two should agree on well-behaved runs, and divergence is the signal. All four side-channel classes (retrievals, tool observations returned into context, context compressions, and periodic summary writes) are first-class reconstruction targets, and omitting any costs a proportional score hit.

\textbf{Epistemics-aware Policy Checkability ($\psi$).} A policy is decidable iff every required field appears in the relevant record set \emph{and} the MPSWM state at the relevant turn is well-formed for the agents it mentions. Using MPSWM rather than raw action fields is what distinguishes $\psi$ from the per-record checkability of \citet{nian2026auditable}: many social policies quantify over \emph{what peer $j$ now knows about principal $i$'s domain}, a property invisible to per-record checks and computable only from an online MPSWM state.

\textbf{Inference-Chain Attribution ($\tau$).} F1 between the attribution graph produced by replaying the log against the MPSWM trajectory and a planted ground-truth graph, with nodes carrying the L0/L1/LX/LR/LF labels introduced in \S\ref{sec:saf:mpswm}. F1 is averaged over chains of length $\geq 2$, so shallow credit for naming the immediate executor cannot inflate the score. The walk-backward construction exploits MPSWM's explicit source-action edges: every item in the disclosed-items set carries the action identifier that produced the belief, so the graph builder does not have to guess.

\textbf{Evidence Integrity ($\sigma$) and Phase-Scoped Policy ($\varphi$).} $\sigma$ is the weighted fraction of records whose integrity level meets the class-specific requirement, with weights $(0.25,0.50,0.75,1.00)$ over the ordinal levels (external, adapter-signed, hash-chained, cross-agent-signed). $\varphi$ is the fraction of phase-scoped policies that are both decidable \emph{and} satisfied within their declared phase: ``discovery messages may not contain financial details'' and ``repair messages must acknowledge the earlier commitment'' cannot be distinguished by a global check from vacuously compliant utterances.

\textbf{Overall score.} The overall audit score is
\[
  \mathrm{AuditScore} \;=\; \prod_{d \in \{s,\psi,\tau,\sigma,\varphi\}} d^{\,w_d},\qquad \sum_d w_d = 1,
\]
with $w_d = 1/5$ by default. The geometric mean is deliberate. If any single dimension collapses toward zero (a broken hash chain, an undecidable policy set, a missing attribution chain), the overall score collapses with it. This mechanically encodes the framework's claim that the five dimensions are jointly necessary; a system cannot compensate for a missing dimension by overperforming on another.

\subsection{Three mechanism classes}
\label{sec:saf:mech}

SAF is realized through three mechanism classes that operate at successive temporal vantage points. \emph{Detect} is pre-episode: a static scan of the scenario specification, persona prompts, and tool manifests for latent policy conflicts that would make a run unauditable before it begins. \emph{Enforce} is runtime: a policy hook fires before every outbound message, before every tool call, and before every memory write, computing a verdict that, depending on the audit condition, is either merely logged or used to block or rewrite the pending action. \emph{Recover} is post-episode: the evaluation pipeline replays the log and the MPSWM trajectory to rebuild the attribution graph and to decide each declared policy, tolerating partial logs via cross-agent references as in the third example. No single mechanism class covers all five dimensions \citep{nian2026auditable}; SAF's benchmark design requires that all three be instantiable under a single runtime switch. The concrete system that realizes the three mechanism classes, including the gateway architecture, the action-record schema, the three audit conditions as a single configuration switch, and the replay cassette that makes evaluation reproducible, is described in Appendix~\ref{sec:appendix:system}.

\section{The ClawSocialArena benchmark}
\label{sec:bench}

Designing a benchmark that exercises multi-party collaboration, security, and privacy under a common audit substrate is itself a non-trivial contribution. Existing social-agent benchmarks either decompose into episodes that stop at privacy or assume cooperation and ignore attacks. We were therefore forced to solve four design problems jointly: find a task family with mechanical verification in each of multi-party collaboration, security, and privacy; design attacker injections that leave clean ground truth rather than mixing attack effects with LLM randomness; let all three axes share a single audit substrate so that SAF scores are directly comparable across them; and generate ground truth without LLM-as-judge so that the headline table is reproducible. This section presents the resulting design.

\subsection{Scenario composition: $150$ total}
\label{sec:bench:categories}

ClawSocialArena contains $150$ scenarios drawn from the seven social categories of AgentSocialBench \citep{wang2026agentsocialbench} (Table~\ref{tab:categories}) and distributed across four strata: $100$ main per-scenario verifiable scenarios (headline SAF, task-success, and attack-rate), $25$ hard-verification scenarios (code review and document editing, LLM-judged halo only), $20$ episode-graph scenarios (five $4$-episode graphs for cumulative-audit evaluation, appendix only), and $5$ named motivating examples (Figure~\ref{fig:vignettes}). The personal-agent setting is fixed: each user is served by exactly one assistant, and multi-agent teams per user are out of scope (\S\ref{sec:discussion}). Profiles and privacy-boundary declarations are reused directly from AgentSocialBench's scenario dataset; the verifiable task layer and attacker taxonomy on top are new.

\subsection{Four verifiable task families}
\label{sec:bench:tasks}

Each main scenario instantiates exactly one of four verifiable task families, each mapped to a subset of the seven categories and verified by a pure-function terminal predicate against final gateway state, with no LLM-as-judge in the headline. \emph{Group Scheduling} (primary axis: multi-party collaboration; categories MC, CU, AM) uses a shared-calendar tool that accepts a booking only on all-agent confirmation, with the final slot required to satisfy every agent's hard constraints. \emph{Consensus Allocation} (multi-party collaboration; CD, MG, HS, CM) uses a shared-ledger tool and checks a fairness predicate on the final allocation (budget split, resource allocation, review-and-merge vote). \emph{Coalition Resistance} (security; CU, MG, HS, CM) uses a shared runbook or review tool and checks whether the legitimate agents reach the target state despite $M$ adversarial agents while respecting the declared delegation-privilege manifest. \emph{Cross-User Inference Containment} (privacy; CD, MC, AM) checks that no privacy invariant in the ground-truth manifest is breached over the action log and the MPSWM joint-decidability state. In addition, a \emph{hard-verification} stratum of $25$ scenarios (code review and document editing) is run with an LLM-judged quality halo that appears only as a supplementary column and never enters SAF or the headline.

\subsection{Three-axis attacker taxonomy}
\label{sec:bench:attackers}

Nine attacker types are binned along three operational axes. The \emph{Multi-Party Collaboration} axis covers \emph{task sabotage}, \emph{consensus blocking}, and \emph{goal hijacking}, in which the attacker blocks consensus, floods the channel, or steers a task toward an adversarial outcome. The \emph{Security} axis covers \emph{prompt-injection propagation}, \emph{delegation-chain abuse}, and \emph{shared-memory poisoning}, in which the attacker injects jailbreaks into peers, escalates privilege through delegation, or poisons shared memory entries. The \emph{Privacy} axis covers \emph{collaborative exfiltration}, \emph{social engineering}, and \emph{cross-user inference}, in which the attacker probes disguised as task-relevant, impersonates or invokes false authority, or probes for cross-user decidability. Each main scenario declares zero or one attacker slot; roughly one third of the $100$ main scenarios are benign (no attacker, serving as the baseline for attack-on versus attack-off deltas), and two thirds are adversarial, split proportionally across the three axes so that each axis receives enough scenarios to support within-axis statistical tests.

\subsection{Scenario generation and validation}
\label{sec:bench:gen}

The main verifiable set contains $100$ scenarios across the seven categories, balanced so that each category carries the task families assigned to it in \S\ref{sec:bench:tasks}; the hard-verification stratum adds $25$ ($12$ code review, $13$ document editing); the episode-graph stratum adds $20$ ($5$ graphs of $4$ linked scenarios, one graph each in CD, CU, MG, HS, AM); the named motivating examples account for the remaining $5$. Scenarios are generated by a four-layer pipeline. The \emph{template} layer declares the structural skeleton for each category-and-family pair (agent count, topology, tool manifest, attack-slot policy). The \emph{instantiation} layer uses an LLM to fill personas, scripted non-player lines, and scenario-specific content, validated against a constraint solver for planted-disclosure coherence and cached by prompt hash so that regeneration does not spend tokens. The \emph{attack-injection} layer inserts the attack plan into the scripted stream for adversarial scenarios. The \emph{ground-truth-assembly} layer emits the ground-truth bundle mechanically from the completed template; no LLM post-hoc labeling of ground truth is used. Each scenario identifier is the content hash of its template and instantiation seed, so every scenario specification is byte-for-byte reproducible. The ground-truth bundle carries a canonical action stream (scripted non-player and attacker actions), a phase schedule, flat and phase-scoped policy sets, a planted attribution DAG with L0 root and expected L1, LX, LR nodes, per-class integrity requirements, a programmable terminal predicate, privacy-and-security invariants, an attack plan for adversarial scenarios, a tool manifest with per-tool audit classes, and a persona manifest. Mechanical ground truth is only as good as the generator; we therefore sample $40$ scenarios uniformly at random, give three independent annotators the template outputs, and ask them to re-produce the four ground-truth artifact classes. We report Cohen's $\kappa$ or Krippendorff's $\alpha$ per artifact class with target $\kappa \geq 0.80$. The $20$-scenario episode-graph stratum shares persistent agent memory across episodes so that cumulative privacy invariants grow with each episode; cumulative metrics (Social Recall trajectory, Social Precision against the growing invariant set, set-based temporal leakage rate, cumulative propagation ratio) are reported in the appendix only.

\section{Discussion, limitations, future work}
\label{sec:discussion}

\textbf{Threat model.} SAF's defensive surface covers malicious peer agents (inter-agent messages, hub aggregation, group channels, addressed by gateway audit hooks and the three-axis attacker taxonomy), prompt-injected agents (inbound message content, addressed by phase-scoped policy enforcement and the tool-invocation-under-attack metric), colluding peers (multi-hop inference chains, addressed by MPSWM-driven online attribution with L0, L1, LX, LR, and LF labels), overprivileged scenario tools (tool-call side effects, addressed by the pre-tool hook and by tool observations as first-class actions), retrieval, memory, and compression side channels (addressed by the four side-channel action types), and well-meaning-but-careless agents (inferential leakage, addressed by epistemics-aware joint decidability over MPSWM). It does \emph{not} defend against a compromised \emph{gateway}: a malicious gateway can rewrite its own action log and MPSWM state, and no amount of hash chaining within the same store would help. We scope this out explicitly because the fix (cryptographic extensions beyond local hash-chain integrity) is a different research direction from benchmark construction, and the integrity ordinal is designed to extend upward along the directions listed below. The \emph{key runtime invariant}, load-bearing for SAF, is that the gateway is the sole cross-agent egress: enforced by the channel adapter that constrains all outbound through the gateway, by network-level isolation, and by a log-completeness check at evaluation time. Any divergence fails the run.

\textbf{Limitations.} (i) The personal-agent setting fixes one assistant per user; market-of-agents and fully-autonomous AI-to-AI networks are out of scope. (ii) Mechanical ground truth inherits generator quality: if the attribution graph or phase schedule is wrong, SAF measures agreement with a buggy specification; the $40$-scenario annotator validation bounds but does not eliminate this. (iii) Simulated non-player users are scripted; a field-channel bridge to Discord or Telegram for human-in-the-loop demonstrations is appendix-only and qualitative. (iv) Rewrite-based enforcement is one intervention style among several (hard reject, ask-agent, learned policy). (v) Three discrete audit conditions, not a continuum. (vi) Evaluation is offline; online streaming evaluation is future engineering. (vii) SAF thresholds are defended but not universally optimal; the $\pm 0.05$ sensitivity analysis bounds threshold dependence. (viii) \emph{Reproducibility is evaluation-layer only, not runtime.} Real agents plus real LLM providers introduce scheduling and completion non-determinism; the cassette mechanism makes evaluation bit-for-bit reproducible, but runtime execution is not. (ix) Only roughly one in three cells runs live on real agents, for cost reasons; every table labels live versus replay. (x) Four models are representative rather than exhaustive.

\textbf{Future work.}
\label{sec:future}
Five directions extend Asymmetric Evidence Integrity beyond local hash chaining and address the compromised-gateway threat scoped out above: \emph{cross-agent Merkle DAGs} that link per-agent chains into a tamper-evident network graph; \emph{decentralized identity with verifiable credentials}, giving each agent a W3C DID whose outbound messages carry signatures that make impersonation cryptographically infeasible; \emph{zero-knowledge proofs of policy compliance} for settings where transcripts cannot be shared; \emph{external anchoring} of log-head hashes to a public ledger or attestation service; and \emph{secure multi-party computation} for hub-and-spoke aggregates that drives hub-aggregation leakage to zero at the protocol level. Beyond cryptography, online streaming SAF evaluation, learned policy hooks, runtime self-attestation, multi-agent teams per user (reworking MPSWM to track epistemic state across intra-user teams), a multi-framework agent panel that admits other personal-assistant platforms alongside OpenClaw on the same gateway, and user-facing audit dashboards are the main threads we plan to pursue.

\section{Conclusion}
\label{sec:conclusion}

ClawSocialArena reframes evaluation for human-centered agentic social networks around auditability as a first-class property of the deployed system: measurable through a five-dimension scoring framework with mechanically emitted ground truth, and interventional through a gateway whose audit hooks can be toggled among three conditions. We contribute a runtime in which $N$ persistent personal-AI-assistant agents communicate only through a central audit gateway, the Social Auditability Framework powered by Multi-Party Social World Modeling, and a $150$-scenario benchmark that extends AgentSocialBench into the multi-party, verifiable-task, attack-aware regime across three axes (multi-party collaboration, security, privacy). We defend the framework through three named motivating examples where a single-agent auditor returns a compliance verdict that SAF correctly overturns, and we preregister the evaluation protocol with numerical results to follow in the camera-ready revision. The release couples the benchmark with the runtime, reference implementations of all baselines, and a pure-function evaluation pipeline whose scorecards are bit-for-bit reproducible from the replay cassette and the ground-truth bundle.

\section{Related work}
\label{sec:related}

ClawSocialArena sits at the intersection of three literatures.

\textbf{Auditability and accountability for LLM agents.} Our framework is most directly a social-setting extension of Auditable Agents \citep{nian2026auditable}, which defines five dimensions (action recoverability, lifecycle coverage, policy checkability, responsibility attribution, and evidence integrity) jointly necessary for a defensible post-deployment audit verdict, together with three mechanism classes (detect, enforce, recover) that realize them across the system lifecycle. That work targets a single-agent system whose action model centers on tool calls. We retain the verdict structure but replace three dimensions with social-setting analogs: lifecycle coverage becomes phase-scoped policy auditability, policy checkability is extended to be epistemics-aware via joint decidability over peers' state as tracked by MPSWM, and responsibility attribution generalizes to inference-chain attribution through L0, L1, LX, LR, and LF labels. Agent Audit \citep{zhang2026agentaudit} complements this picture by providing static analysis of agent code and tool-manifest configurations; it addresses pre-deployment \emph{detect}, not runtime \emph{enforce} or post-hoc \emph{recover}, and does not consider multi-agent action chains. Reporting infrastructure for accountability, for example model cards \citep{mitchell2019modelcards}, motivates the Auditability Card reporting artifact used by \citet{nian2026auditable}; our per-scenario ground-truth bundles and per-run scorecards inherit the same posture.

\textbf{Privacy and security benchmarks for multi-agent LLM systems.} Nissenbaum's contextual-integrity framework \citep{nissenbaum2004privacy} grounds a family of LLM privacy benchmarks: ConfAIde \citep{mireshghallah2024confaide}, PrivacyLens \citep{shao2024privacylens}, PrivLM-Bench \citep{li2024privlm}, CIMemories \citep{cimemories2025} for persistent memory, MAGPIE \citep{juneja2025magpie} for multi-agent teams, MAMA \citep{liu2025mama} for topology-aware memory leakage, AgentLeak \citep{elyagoubi2026agentleak} as a full-stack harness, and AgentDAM \citep{agentdam2025} for autonomous web agents; \citet{he2025emerged} survey the area. AgentSocialBench \citep{wang2026agentsocialbench} is the direct ancestor of our scenario set: it provides user profiles, privacy-boundary declarations, and seven social categories as static scenario specifications, and it reports per-episode privacy-leakage metrics via LLM-as-judge pipelines. We reuse its profiles and privacy-boundary layer, lift its static scenarios into runnable multi-party deployments, add a verifiable task layer and a three-axis attacker taxonomy on top, and replace LLM-as-judge scoring on the headline with mechanical ground truth derived from the audit log and the scenario generator's planted artifacts.

\textbf{Social simulations and multi-agent platforms.} Generative Agents \citep{park2023generative}, SOTOPIA \citep{zhou2024sotopia}, OASIS \citep{oasis2024}, AgentSociety \citep{piao2025agentsociety}, $\mathrm{S}^3$ \citep{gao2023s3}, and WarAgent \citep{hua2024warandpeace} target population-level or scripted social dynamics; MultiAgentBench \citep{zhu2025multiagentbench} evaluates collaboration and competition for cooperative multi-agent teams; the Moltbook ecosystem \citep{jiang2026moltbook,moltbook2026socialization,moltnet2026,collective2026moltbook} studies agent-native platforms observationally. Cooperative-team frameworks \citep{hong2024metagpt,wu2023autogen,chen2024agentverse,li2023camel,qian2025scaling} assume shared rewards and are orthogonal to multi-principal auditability. OpenClaw \citep{openclaw2025} is the open-source personal-AI-assistant platform whose agents we deploy: each user's assistant runs persistently with a persona, a memory store, and a plugin-based channel interface. On conversational agents, $\tau$-bench \citep{yao2024taubench} and $\tau^2$-bench \citep{barres2025tau2bench} formalize single-user tool-agent-user coordination as a Dec-POMDP \citep{oliehoek2016decpomdp}; our setting retains the Dec-POMDP framing but the agents and users are themselves distinct principals whose commitments must be jointly auditable. In the software-agent domain, the analogous move from one-shot to continuous evaluation has already exposed large gaps between instantaneous capability and long-horizon performance \citep{deng2026evoclaw}; our work makes the analogous move for social agents under the additional constraint that auditability is itself a measurable property of the deployed system.

\section{System design of ClawSocialArena}
\label{sec:appendix:system}

This appendix describes the concrete system that realizes SAF's \emph{Detect}, \emph{Enforce}, and \emph{Recover} mechanism classes under a single configuration switch. The system brings $N$ personal-AI-assistant agents and a central audit gateway together into one live multi-party deployment; every message between agents, every tool invocation, every memory write, every retrieval, and every context compression flows through the gateway, which records an immutable hash-chained entry, updates MPSWM online, and, depending on the audit condition, either lets the action proceed, logs a verdict, or blocks or rewrites it before it takes effect. Figure~\ref{fig:runtime} shows the layout.

\subsection{System architecture}
\label{sec:appendix:system:layout}

The runtime is composed of three parts. First, $N$ persistent personal-AI-assistant agents run as separate processes on a private network, one per simulated user, each with a preloaded persona, a memory store, and a tool manifest. Second, a single audit gateway runs on the same network and holds all shared state (the action log, the MPSWM state, the attribution graph, the phase tracker, the policy-hook registry, and the replay cassette). Third, the scenario's tools are hosted inside the gateway rather than as per-agent sidecars. A lightweight channel adapter loaded into each agent routes every outbound message, tool invocation, memory write, retrieval, and context compression through the gateway, and a network-level egress firewall closes every other outbound path. Together, these commitments make the gateway the only place where any graph-visible action is observable, which is the property that lets the runtime compute a per-agent audit trail at all.

\subsection{Actions and the audit log}
\label{sec:appendix:system:actions}

The gateway records ten action types into a per-agent hash-chained log. Five are \emph{first-class} actions that an agent emits visibly: LLM invocations, tool calls, outbound peer messages, memory writes, and delegation spawns. One is a \emph{control-plane} action produced by the runtime itself: the policy verdict returned by an audit hook. The remaining four are \emph{side-channel} actions that a tool-call-centric log typically elides: the return of a tool observation into an agent's working context, a retrieval from an external store, the compression of a long context window, and a periodic summary write to long-term memory. Logging all ten is what lets SAF catch leaks that flow through retrieval, summarization, and compression rather than through overt messages. Each recorded action is materialized as an immutable record roughly equivalent to the following Python dataclass:

\begin{verbatim}
@dataclass(frozen=True)
class ActionRecord:
    action_id: str                # UUID
    prev_hash: str                # sha256 of prior record by this agent
    agent_id: str
    action_type: str              # one of ten types (see above)
    timestamp: float
    execution_phase: str          # nominal | retry | fallback | approval | delegation
    social_phase: str             # discovery | negotiation | disclosure |
                                  #   boundary-setting | repair
    payload: dict                 # type-specific
    integrity_level: int          # 1=external, 2=adapter-signed,
                                  # 3=hash-chained, 4=cross-agent-signed
    signature: Optional[str]      # present iff integrity_level >= 3
\end{verbatim}

Hash chains are per-agent: a truncation on one agent remains locally diagnosable and is recoverable from peers' cross-references in inbound-message payloads, a property that the third motivating example exercises directly.

\subsection{Scenario lifecycle}
\label{sec:appendix:system:loop}

A scenario run proceeds through five stages. The runtime loads the scenario together with its ground-truth bundle, brings up the gateway and the scenario's tools, brings up the $N$ agents with the channel adapter preloaded, and then begins to drive the scenario by delivering opening messages and any scripted non-player or attacker actions. Each agent responds through its channel adapter, which routes back through the gateway; the gateway evaluates the relevant policy hook on every outbound message, tool call, and memory write, appends an action record, updates MPSWM and the phase tracker, and extends the attribution graph. The run terminates when the task-family terminal predicate passes or a per-scenario turn cap is reached, at which point the agents and gateway shut down and the run artifact (action log, shadow log, replay cassette, final world state) is emitted for offline evaluation. Two system-level invariants hold across every condition. \emph{Gateway-as-sole-egress:} every graph-visible action routes through the gateway, enforced at three layers (the channel adapter that constrains all outbound to the gateway-facing send, the network-level egress firewall, and a log-completeness check at evaluation time that compares each agent's internal audit trail against the gateway's per-agent log, with any divergence failing the run). \emph{Failures as first-class actions:} timeouts, refusals, exceptions, and truncations are recorded with the same integrity guarantees as completed actions, so that an audit over a run that experienced failures remains defensible; a broken hash chain, by contrast, is fatal and invalidates scoring.

\subsection{The three audit conditions}
\label{sec:appendix:system:conditions}

The gateway supports three operating modes, selected by a single configuration switch. Under \textsc{baseline}, the gateway behaves as a passthrough: it forwards messages and tool calls with only a minimal transport record for reproducibility, and does not hash-chain, does not update MPSWM, does not fire any policy hook, and does not write to the shadow log. This mode simulates a deployed system with no audit infrastructure. Under \textsc{passive}, the full audit substrate is active: every policy hook computes and logs its verdict, MPSWM and the attribution graph are extended on every action, and the shadow log is double-written, but verdicts are never allowed to block or rewrite an in-flight action. This mode isolates the measurement value of auditability from its intervention value. Under \textsc{enforce}, the same stack may block a violating action or replace it with a sanitized substitute before it reaches its recipient. The task-success delta between \textsc{enforce} and \textsc{passive} is reported as a quality-of-rewrite diagnostic alongside, but separate from, the headline, so that interventions that break task semantics stay visible rather than hidden inside an aggregate.

The three conditions are implemented as a single branch at the gateway:

\begin{verbatim}
async def on_action(self, action: ActionRecord) -> ActionRecord:
    if self.condition == "baseline":
        return action  # passthrough; no hash, no hook, no MPSWM update

    self.mpswm.update(action)
    verdict = self.hooks.evaluate(action, self.mpswm)
    self.action_log.append(action)
    self.shadow_log.append(action)
    self.action_log.append(verdict.as_record())  # control-plane action

    if self.condition == "passive":
        return action  # verdict is logged but never applied
    # condition == "enforce"
    if verdict.decision == "block":
        return self._synthesize_refusal(action, verdict.reason)
    if verdict.decision == "rewrite":
        return action.with_payload(verdict.rewrite_payload)
    return action
\end{verbatim}

A policy hook is any object satisfying:

\begin{verbatim}
class PolicyHook(Protocol):
    def evaluate(self, action: ActionRecord,
                 mpswm: MPSWMState) -> PolicyDecision: ...

@dataclass
class PolicyDecision:
    decision: Literal["allow", "block", "rewrite"]
    reason: str
    rewrite_payload: Optional[dict] = None
\end{verbatim}

\subsection{Determinism and the replay cassette}
\label{sec:appendix:system:determinism}

Runtime execution is non-deterministic by construction: LLM completions, agent scheduling, and network timing all introduce variability that the system does not attempt to suppress. To preserve reproducibility at the evaluation layer, the gateway runs a replay cassette that captures every LLM completion, every tool invocation, and every audit decision during a live run. The offline evaluation pipeline (SAF scoring, attribution-graph reconstruction, cumulative metrics) is then bit-for-bit deterministic given the cassette. A direct consequence is a live-versus-replay split across the benchmark: a subset of scenarios runs live with real agents and real providers, while the remainder replays cassettes recorded on a single frontier model under \textsc{passive} at other model-and-condition cells; every results table labels which cells are live and which are replay.

The cassette's external API is intentionally small:

\begin{verbatim}
class Cassette:
    """Append-only keyed log of LLM completions, tool calls, and audit decisions."""
    def record(self, key: CassetteKey, value: Any) -> None: ...
    def playback(self, key: CassetteKey) -> Any: ...

# Live run: capture
completion = await llm.complete(prompt)
cassette.record(("llm", agent_id, seq), completion)

# Replay: deterministic lookup
completion = cassette.playback(("llm", agent_id, seq))
\end{verbatim}

Replay uses the cassette to substitute for every outbound call the gateway would otherwise make, so the same scenario can be re-scored under a different audit condition without re-running the agents.
